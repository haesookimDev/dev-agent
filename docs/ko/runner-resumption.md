# 사용자 결정 이후 Runner 개발 재개

한국어 | [English](../en/runner-resumption.md)

## 실행 계약

Runner 대기 루프는 `/api/runs/{id}/commands`의 현재 `status`를 기준으로 다음 실행을 결정합니다. 피드백·승인 Row는 이력이지 실행 권한이 아닙니다. [Worker API 전환 권한](worker-transition-authority.md)과 함께 적용하며 사용자 승인을 Runner가 대신 생성하지 않습니다.

| 조회한 상태 | Runner 동작 |
| --- | --- |
| `implementing` | 사용자 결정으로 허용된 개발·독립 검증을 재개 |
| `budget_exhausted`, 입력·피드백·승인 대기, 그 밖의 상태 | 실행하지 않고 다음 조회까지 대기; 미처리 피드백 Cursor 유지 |
| `committing` | `delivery.ready`를 기록하고 종료; 전달은 Control Plane 소유 |
| `pr_created`, `completed`, `failed`, `cancelled` | 오래된 피드백보다 종료 상태를 우선하여 종료 |

예산 승인 또는 PR 거절이 `implementing`으로 바꾸면 새 피드백이 없어도 재개합니다. 승인 이력 Cursor가 이미 진행됐어도 현재 허용 상태를 관측하면 재개할 수 있습니다. 피드백이 있으면 순서대로 적용하고 직전 독립 검증이 실패했다면 그 오류 내용도 전달합니다. 수리 횟수 제한, 검증 성공 후 산출물·Patch 업로드, 승인 대기, 예외 시 실패 보고·세션 정리는 유지합니다. 서버 이벤트 Message는 예산 재개도 정확히 설명하도록 `Feedback` 전용 표현에서 `Authorized` 표현으로 바꾸었으며 상태·Event Type 계약은 그대로입니다. UI 상태 번역은 변경하지 않았습니다.

API Schema·사용자 권한·Origin 검사·DB Migration·운영 기본값·의존성·환경변수 변경은 없습니다. 기존 Runner를 새 버전으로 교체하면 적용됩니다. 이미 실행 중인 프로세스를 자동 교체하거나 과거 작업을 강제 재개하지 않습니다.

## 실제 화면과 한계

운영 Web Build를 위 실제 OIDC API·Runner에 연결했습니다. 합성 Session을 제한된 일회용 로컬 Cookie 경로로 전달하고 비밀값은 출력하지 않았습니다. 사용자 피드백·예산 승인·PR 거절·승인은 올바른 Origin을 사용하는 별도 인증 HTTP로 수행했습니다. 로컬 HTTP 페이지는 OIDC의 HTTPS Origin과 달라 브라우저 변경 성공이나 외부 IdP 로그인을 검증한 것이 아닙니다. 인증·TLS·시스템 신뢰를 낮추지 않았습니다.

화면은 새로고침 없이 다음을 반영했습니다: 피드백 이후에도 예산 소진/Version 6/실행 1회 유지, 예산 승인 후 승인 대기/Version 9/255분/실행 2회, `revision.json` 미리보기의 `{"turn":2}`, PR 거절 후 Version 12/실행 3회, 최종 승인 후 전달 준비·Session 종료/Version 13/프로세스 종료 0. 한국어·영어 390px 화면의 문서 폭은 375px이고 가로 넘침 없이 `커밋 중`/`Committing` 75%·Live와 닫힌 피드백을 표시했습니다. 이 합성 환경은 실제 전달을 실행하지 않아 작업을 완료·PR 생성 상태로 조작하지 않았습니다.

관측 구간 브라우저 요청 55개는 모두 200이고 외부 요청·Console 메시지는 없었습니다. 처음 Web 실행에서 잘못 선택한 standalone 경로를 실제 생성 경로로 수정한 뒤 확인했습니다. 관찰 도구의 연결 오류에는 서비스·같은 탭의 생존을 재확인하고 이어갔습니다. 내장 브라우저의 양 언어 스크린샷은 확인했지만 Computer-use 캡처는 다른 작업 화면이어서 대상 네이티브 화면·입력 성공 증거로 사용하지 않습니다. Escape 입력도 대화상자 닫힘이 확인되지 않아 성공으로 기록하지 않습니다. UI·네이티브 기능 변경은 없습니다.

전체 데스크톱은 비공개로 유지했고 공개 공유 권한을 변경하지 않았습니다. 소유한 화면·터미널·API·Runner·Web과 일회용 데이터를 정리하고 13100/18100/13500/18500/18501 포트 해제를 확인했습니다. 자동 생성된 Web 타입 경로는 운영 Build로 복원됐으며 미커밋 UI 변경은 없습니다.

## 후속 작업과 롤백

실제 사용에서 예산 소진 페이지에 예산 승인 버튼이 없음을 확인했습니다. API·Runner 재개와 별개인 사용자 제어 UI 후속 작업으로 다룹니다. 명령 조회 이후 발생하는 취소와 실행 사이의 경쟁, 신뢰할 수 없는 VM의 물리적 정지·실제 시간 예산 강제, 실제 KVM/Preview 격리와 MVP 전체 완료는 별도 검증이 필요합니다.

정상 Revert로 Runner를 되돌릴 수 있으며 Migration은 없습니다. 이전 Runner는 승인 전에도 먼저 실행할 수 있고 승인 후에는 정체할 수 있습니다. Worker API의 403만으로 이미 시작한 모델 실행을 중단할 수는 없으므로 롤백 위험을 평가하고 API 승인 경계를 끄지 않습니다.
